# Ed25519 acceptance review and verification record — issue #7

Reviewed 12 October 2026 against audited commit
`14edc43ac9b5e8acfd746c08393edd869c931882` and the implementation commit recorded
in `ed25519-fixed.json`. This is a focused source review and reproducible
verification exercise, not a claim of external cryptographic certification.

## Decision and normative basis

[Profile §2](../profile.md#ed25519-acceptance-profile) is normative. Require
canonical on-curve A and R, reject points of order dividing 8 (including the
identity), require S < L, and verify the uncofactored equation with the SHA-512
challenge reduced modulo L. The message remains the existing 64-byte
eddsa-jcs-2022 signing input.

- [RFC 8032 §§5.1.3 and 5.1.7](https://www.rfc-editor.org/rfc/rfc8032#section-5.1.7)
  supply point decoding, the scalar range and the verification equations.
  The RFC requires the cofactored equation and permits an uncofactored check
  as sufficient. It does not require excluding all small-order points.
- Selecting a reduced-challenge uncofactored equation and excluding small-order
  A/R are profile choices. Reduction of the challenge matters for mixed-order
  points under an uncofactored check, so it is specified explicitly. Reduction
  cannot change the RFC's cofactored equation because [8L]A = O.
- Mixed-order points are NOT equivalent to small-order points. A point with
  both prime-order and torsion components remains admissible if the exact
  equation holds. No prime-subgroup membership check is silently added.
  This agrees with the independent CCTV expectations used here and current
  libsodium verification. It is deliberately different from ZIP-215.
- [CCTV's discussion and point enumeration](https://github.com/C2SP/CCTV/tree/50a8ecf2a220f4c8bdc4f085789b8e85c26829e7/ed25519)
  and [“It's 255:19AM”](https://hdevalence.ca/blog/2020-10-04-its-25519am)
  explain why backend names alone do not determine consistent acceptance.

The profile restriction eliminates the universal identity-key construction
A = O, R = B, S = 1 and the other small-order cases. This concerns a degenerate
key chosen for a log; it demonstrates neither recovery of an honest private
key nor takeover of a log secured by an honestly generated key. Ordinary
signatures, including randomized valid signatures, remain admissible. Existing
logs that relied on degenerate signatures can become invalid under this rule.

## Enforcement review

All entry proofs, witness proofs and the standalone proof primitive reach the
library verifier. Checks live there, not just in driver request parsing.
Multikey/parameter syntax and authorization order are unchanged: a syntactically
well-formed weak key can be listed, but its proof cannot authenticate anything.
An authorised weak entry proof reports `invalid-proof`; a weak witness does not
count toward the threshold. Independent fixtures also exercise partial validity
and explicit version selection after an invalid second entry.

The byte/integer guards mask the sign bit, require y < p, and reject the five
small-order y coordinates, covering all eight points and their six alternative
encodings. The forbidden sign-of-zero encodings have y = 1 or p - 1 and are
already excluded. Backends still perform curve decoding, S-range checks and the
signature equation. The guards do not implement signing or elliptic-curve
arithmetic. Python and TypeScript additionally check S explicitly.

| Implementations | Enforcement |
| --- | --- |
| Python, TypeScript, Elixir, Go, Swift, Kotlin, Common Lisp, Ruby, Java, OCaml, Dart, Scala, Gleam | Canonical/non-small-order A/R guards before backend verification. |
| Rust | dalek `verify_strict` plus an explicit canonical public-key encoding check. |
| Zig | A/R guards plus `verifyStrict`; the default `verify` is cofactored. |
| C# | NSec 26.4.0/libsodium 1.0.22 verification. Bouncy Castle 2.6.2 signing retained; its verifier accepted nonzero torsion residues. Both packages are locked. |
| C, C++, Forth, PHP, Raku, Ada, Lua, Haskell | Existing libsodium verifier already enforces this policy; no production change needed. |

The independent mixed-order fixtures caught the Zig and C# cofactored behavior.
The final implementations accept the mixed-order positive controls and reject
the nonzero-residue cases. This prevents solving the original issue with an
identity-only blacklist or an overbroad rejection of every mixed-order key.

## Reproduction of the reported discrepancy

`ed25519-baseline.json` retains actual observations from an unmodified archive
of the audited commit, with exact runtime/backend versions, expected outcomes
and actual outcomes. Node was 24.21.0 with OpenSSL 3.5.8; Python was 3.12.15 with
cryptography 50.0.2 and its bundled OpenSSL 4.0.3.

For example, `low-order-A-0100…0000` uses A = O, R = B, S = 1 in a correctly
hashed, authorised genesis log. Python's standalone proof primitive and full
resolver both returned valid; Node's primitive returned false and resolver
reported `invalid-proof`. `identity-witness` independently reproduces a witness
threshold difference. The raw-library record separately exercises 914 CCTV and
151 Wycheproof signatures, including ordinary positive controls. Expected
outcomes are grouped with the complete vector ID lists; they are not inferred
from either runtime's responses.

The original audit's exact construction file was not available in this checkout.
These are newly constructed, independently reproducible full-log cases for the
reported class, not a claim to have recovered its missing transcript. The
Python/Node discrepancy is now directly confirmed for the recorded inputs and
versions; no assertion is made about all historical versions or platforms.

## Coverage and retained evidence

- `ed25519-baseline.json`: audited-commit Python/Node direct raw-library results,
  driver proof-library results and full resolver results, with expected/actual
  outcomes and runtime versions.
- `ed25519-fixed.json`: the same record after the fix, including the exact
  implementation commit and fixture digest. All expected outcomes match.
- `ed25519-runtime-versions.json`: toolchain/backend version command outputs for
  the macOS arm64 verification environment. Crypto dependencies are additionally
  pinned in the repository's language lockfiles; Swift on this host uses
  Apple CryptoKit.
- `ed25519-conformance.txt`: all **24** registered implementations checked against
  **89** independent boundary fixtures each: **42** standalone proof-library
  driver calls and **47** resolver calls (2,136 total). This is not a claim of
  running the raw CCTV/Wycheproof corpus in all 24 libraries; those direct raw
  API tests were run in Python and TypeScript.
- `ed25519-interop.txt`: the pre-existing full interoperability suite, 9,480
  checks across all 24 implementations. Shared-oracle agreement is supplemental
  evidence, not the basis of the new expected outcomes.

All 24 names are printed in the conformance transcript. Local unit/static checks
also passed for TypeScript, Python, Rust, Elixir, Go, Kotlin, Zig, Common Lisp,
Dart and Gleam. Local Swift unit compilation was blocked by the installed Apple
SDK's missing `TestingMacros` plugin; the Swift release build, all independent
boundary cases and the full interop suite passed. The PR's Linux CI runs Swift
unit tests and the full all-implementation boundary suite.

## Reproduce

The sources and licenses of the independent corpora are in
[`vectors/ed25519/README.md`](../../vectors/ed25519/README.md). No network is
needed for the checked-in corpora or fixture construction.

```sh
python3 tools/ed25519-fixtures.py
node harness/run.ts
node --test harness/ed25519.test.ts
node --test implementations/typescript/test/ed25519-policy.test.ts
(cd implementations/python && uv run pytest tests/test_ed25519_policy.py)
python3 tools/ed25519-record.py --commit "$(git rev-parse HEAD)" --out /tmp/ed25519-record.json
```

To reproduce the baseline, archive the audited commit into a separate directory
and pass it as `--root` to `tools/ed25519-record.py`. That script uses the current
independent fixtures with the selected tree's unmodified Python/Node libraries
and drivers. It records observations even when old behavior violates the new
profile; it is an evidence recorder, not a passing conformance test. CI runs the
asserting tests and checks that independent boundary fixture regeneration is
byte-for-byte reproducible.
