# vh

[![interop](https://github.com/brianorwhatever/vh/actions/workflows/interop.yml/badge.svg)](https://github.com/brianorwhatever/vh/actions/workflows/interop.yml)

This repository has interoperable implementations of
[VH-Log](https://swcurran.github.io/VH-Log/next/), Stephen Curran's
**Verifiable History Log**, in twenty-four languages, plus a shared test suite that
checks the implementations against each other.

VH-Log is an append-only, hash-chained JSON Lines log of a versioned `state`
object:
- a self-certifying identifier (SCID) derived from the genesis entry;
- eddsa-jcs-2022 proofs from authorised update keys, with optional
  pre-rotation;
- optional witnesses and watchers.

It is the log under did:vh and (in future) did:webvh.

## How interoperability is tested

```
vectors/                    shared, language-neutral test data
  primitives.json           JCS, multihash, multikey, key hash, SCID, entry hash, proofs
  resolution/*.json         158 logs (valid and invalid), each with the expected result
  generation.json           scenarios each implementation must reproduce exactly
harness/run.ts              runs every implementation's driver against all of it
implementations.json        how to build and start each driver
```

Each implementation ships a **driver**: a process that speaks a small JSON
Lines protocol ([`docs/interop-protocol.md`](docs/interop-protocol.md)) on
stdin/stdout. The harness runs five suites against every driver:

1. **primitives** — byte-exact encodings, hashes and signatures.
2. **resolution** — the resolver's verdict on every vector log: validity, error
   code, failing version, state and metadata.
3. **generation** — Log Controller operations produce the same entries as the
   reference. Ed25519 and JCS are deterministic, so they must match exactly.
4. **cross** — every implementation resolves the logs and witness files that
   every other implementation generated.
5. **didwebvh-ts** — an independent check. VH-Log was extracted from did:webvh, so
   both share SCID derivation, entry hashing, eddsa-jcs-2022 proofs, pre-rotation
   key hashes and witness proofs. [`vectors/external/didwebvh-ts`](vectors/external/didwebvh-ts)
   holds did:webvh logs produced by the independent
   [didwebvh-ts](https://github.com/decentralized-identity/didwebvh-ts)
   implementation: key rotation, pre-rotation, witnesses and deactivation. Every
   implementation must reproduce each SCID and entry hash and verify each proof.
   This catches mistakes that all the implementations could otherwise share,
   since they were all built against the same reference.

```sh
node harness/run.ts                            # everything
node harness/run.ts --impl rust --impl python  # a subset
node harness/run.ts --suite resolution --group witnesses --verbose
```

### The interop profile

VH-Log leaves some choices to specialisations, and a few behaviours are open:
- how a proof names its key;
- what a witness signs;
- whether an invalid later entry voids the whole log;
- which error a resolver reports.

Implementations that are tested against each other must make the same choices.
[`docs/profile.md`](docs/profile.md) records those choices, including a shared
error-code list and check order. Issues found in the spec along the way are in
[`docs/spec-notes.md`](docs/spec-notes.md). Among them: the spec's only worked
entry-hash example doesn't reproduce.

## Benchmarks

The [website](https://brianorwhatever.github.io/vh/#benchmarks) compares warm
request latency for creation, signing, and resolution with and without witnesses.
Each result includes machine context and downloadable samples. These measure the
JSON Lines drivers, including transport overhead; they are not isolated library
or general language benchmarks.

```sh
node benchmarks/run.mjs   # build and measure all implementations
node site/build.mjs       # render the measured snapshot
```

See [methodology and reproduction](benchmarks/README.md) for workloads, warmup,
measurement boundaries, and the Swift driver's distinct signing path.

## Development

Toolchains: Node ≥ 24, Rust stable, [uv](https://docs.astral.sh/uv/) (Python
3.12), Elixir ≥ 1.18 / OTP ≥ 27, Go ≥ 1.22, Swift ≥ 6.0, JDK ≥ 17, Zig 0.17,
SBCL (developed with 2.6.9), and 64-bit Gforth 0.7.3 with a C++17 compiler,
libtool, libsodium, utf8proc and nlohmann/json (see the [Forth setup](implementations/forth/README.md)).

```sh
node tools/generate-vectors.ts   # regenerate vectors after changing the reference implementation
node harness/run.ts
```

When adding vectors, build each invalid log so that **exactly one** check
fails. The generator checks every vector against the reference resolver as it
writes it.

To add an implementation:
1. Write a driver for the protocol.
2. Add it to `implementations.json`.
3. Run the harness until it is green, then `node harness/run.ts --update-readme`.
4. Give it a job in `.github/workflows/interop.yml`.
5. Add it to the presentation page: in [`site/build.mjs`](site/build.mjs),
   add it to `LANGS` and `PARTS` and give each movement its line ranges and
   beat texts. `node site/build.mjs` fails if a beat's text isn't in the code.

CI ([`.github/workflows/interop.yml`](.github/workflows/interop.yml)) runs each
implementation's own checks, verifies that the vectors are up to date, and
runs the full matrix.

The C, C++, C#, Java, Ruby and PHP drivers also have boundary tests:

```sh
node --test harness/driver-regressions.test.ts
# Select one after building it with the harness:
VH_TEST_IMPLS=c node --test harness/driver-regressions.test.ts
```

The five newest libraries also run the boundary suite:

```sh
node harness/run.ts --impl dart --impl haskell --impl lua --impl gleam --impl scala --impl typescript
VH_TEST_IMPLS=dart,haskell,lua,gleam,scala node --test harness/driver-regressions.test.ts
```

Their toolchains are Dart ≥ 3.6, GHC ≥ 9.6, Lua ≥ 5.4, Gleam ≥ 1.19 with
Erlang/OTP ≥ 28, and Scala CLI with JDK 21. Haskell and Lua also require
libsodium and pkg-config; Lua needs development headers and a C++17 compiler.
Each implementation's README includes setup and direct library usage.

The C, C++, C#, Java, Ruby and PHP toolchains are C11/C++17, .NET 10, JDK 21, Ruby ≥ 3.4
with OpenSSL 3, and PHP ≥ 8.3 with Sodium and mbstring. C uses json-c; C++
uses nlohmann/json; both use libsodium. See each implementation’s README
for installation and library usage.
