Sixteen implementations of VH‑Log that produce the same bytes.

TypeScript, Rust, Python, Elixir, Go, Swift, Kotlin, Zig, Common Lisp, Forth, C, C++, C#, Java, Ruby and PHP, checked against each other and against didwebvh-ts on every push. Below: four algorithms that matter, in all sixteen, one beat at a time.

Every eddsa-jcs-2022 proof signs SHA-256(JCS(proof config)) followed by SHA-256(JCS(document)). Sixty-four bytes, built the same way in every language.

III Verifying the SCID

The identifier is a hash of the first entry as it was before the identifier existed. To check it, a resolver puts the {SCID} placeholder back, as text, and hashes again.

IV Pre-rotation

A log can commit to the hashes of its next keys. While it does, every new update key must hash to one of those commitments, or the entry is rejected.

What the spec leaves open

Building it sixteen times turned up 21 notes on the spec. The first one: the worked example in Generate Entry Hash does not reproduce.

All 21 spec notes

Where the spec leaves a choice open, the interop profile makes it once, for all sixteen:

  • A proof names its key as did:key:<mk>#<mk>.
  • A witness signs {"versionId": …}, as in did:webvh.
  • Every proof on an entry must be valid and authorised, not just one.
  • The first invalid entry ends the log. The valid prefix still resolves, with an invalid-entries warning.
  • Failures carry one shared error code, found in one shared check order.

Add a language

A seventeenth part is welcome. It joins the matrix, and the page, by passing the same tests as the other sixteen.

  1. Read the documents, not the code

    Work from the pinned spec, the interop profile, the driver protocol and the shared vectors. Zig and Common Lisp were built that way, so each is an independent check that the documents are enough. Note anything you had to guess.

  2. Write a driver

    One long-running process that reads a JSON request per line on stdin and writes a JSON response per line on stdout. Split on \n only, parse numbers as doubles, and keep stdout for responses. It answers 12 operations:

    jcs hash multikey key-hash scid entry-hash sign verify resolve create update witness

  3. Register it

    Add an entry to implementations.json: where it lives, how to build it, how to start the driver.

    {
  "name": "ocaml",
  "cwd": "implementations/ocaml",
  "build": ["dune", "build"],
  "command": ["_build/default/bin/vh_log_driver.exe"]
}

  4. Run the harness until it is green

    node harness/run.ts --impl ocaml              # your driver alone
node harness/run.ts                           # everyone, including cross
node harness/run.ts --update-readme           # regenerate the matrix

    Then give it a job in interop.yml that runs its own tests, and add it to the interop job's toolchains.

  5. Put it in the score

    In site/build.mjs, add the language to LANGS and PARTS, then give each of the four movements a line range and the text of each beat. The build reads the code from your files and fails if a beat's text isn't found, so the page can't show code you don't have. Counts, the matrix and every "sixteen" on the page update on their own.

    "ocaml": { ranges: [["ocaml/lib/proof.ml", 40, 43]],
  marks: [[1, "sha256 (canonicalize config)"],
          [2, "sha256 (canonicalize document)"],
          [3, "^"]] },
